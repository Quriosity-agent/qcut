# QCut v2026.11.17.1

### Fixed

- The editor notices a media file that was written over in the project folder. It keeps a copy of its own of every file it imports, and the preview and the in-editor export play that copy; the native export reads the file in the folder. A file rendered again under the same name left the two apart, so the preview went on showing the old shot while the exported file held the new one, and nothing said so. The editor now compares each file's size and modification time with what it copied and reads the ones that changed: when its window is looked at again, once a project's media has loaded, before `editor:timeline:apply` and a batch add, and before every export. A file from before this was recorded is compared by size. `editor:media:refresh` asks for the check outright and lists what was read again; `POST /api/claude/media/:projectId/refresh` does the same. An export through the renderer engine is refused while a changed file that the timeline plays could not be read, or while the check has not answered, since it would draw the old copy; a native export does not wait for the check. A file is the item's when its path is spelled as the item's is; another spelling (`Logo.png` for `logo.png`) counts only where the folder's file system takes the two for one file. A check goes on past an item that is removed while its file is read (it stopped there and answered as if every file had been looked at), lists that item with the failures, and fails outright when the project is closed or another one opened before it is through, also while its folder is still being scanned. A thumbnail, a size or a length still being measured from the old file when the new one is read no longer lands on the item, and a look at the window that comes within three seconds of the last check is made up for once the three seconds are over. Whoever asks for a check while one is under way gets the run that follows it, not the answer of the one that had listed the folder before.
- `editor:media:rename` takes the clips along. A media id is made from the file's name, so a renamed file had a new id while its clips kept the old one: the preview still played them, and the native export left them out and reported success. The editor's item now gets the new id, name and path, every clip that played the old id plays the new one (in every scene, on locked tracks too), and so do the stickers. The undo and redo steps are pointed at the new id too, so undoing an earlier edit does not bring the old id back. The rename is all or nothing: if the editor cannot follow (a scene that cannot be saved, a copy that outlasts the wait, the project closed or another project or scene opened meanwhile), it takes back what it had changed and the file is put back under its old name; another project that is open by then is left alone, though its media can bear the same ids. A file is never moved onto one that appeared under the new name meanwhile: it takes the next free name, or is refused when that very name was asked for (on a volume without hard links the file is copied to the new name, which takes as long as the file is large, and a symbolic link is made again under it; a copy that breaks off is taken away again, and where it cannot be, the part that is left keeps the file's restricted metadata and the command says that the file is under both names). When the editor's answer does not come in time, or says that not everything could be taken back, the editor is asked to end on the old id before the file goes back. When the file cannot be put back (its old name was taken meanwhile), the editor is asked to follow it under the new name instead, and the rename then stands: the command succeeds with a `warning`. The desktop app notes every rename before it moves the file, does not make a rename it cannot note, and keeps the note until the editor is known to be where the file is, so a request that never reaches the editor (it was reloaded, its window is gone) or an app closed in the middle of a rename leaves nothing apart for good: what is not settled then is settled from the name the file has when the project is next opened, and the renamed file is told from another file that has taken its old name by its size and the time it was changed. While the app is at work on a rename the editor leaves it alone, however long that takes (a large file copied on a volume without hard links): the app says which renames it is at work on, and nothing is read off the age of a note. A second request does not begin a rename between two names while another is making one. An item is brought over to the renamed file only when the editor held it before the rename began and it was copied from a file of that size and time, and it is taken for another file's only when the editor came to hold it after the rename began, from a file of another size or time. So another file that has taken the old name and become a media item of its own keeps its item and its clips, also when it is as long and as old as the renamed file (the same clip brought in twice); and an older copy of the renamed file itself (the file was written over shortly before it was renamed) is not given up to the other file. Where nothing tells the two files, or whose an item is, nothing is changed and the note is kept. Until a rename is settled, the check of changed files leaves its items as they are and lists them as not read; when the notes of renames cannot be read at all, the check changes nothing and fails saying so. The rename saves the open scene with the tracks it holds, under its own project and scene, so a project opened in that moment is not written to. A restricted file's metadata goes with it without touching another file's: metadata that a file of the new name already has is neither written over nor removed when the rename gives up, also when the two are changed from different processes of the app at once (the HTTP API and the app's own media handlers). A change the HTTP API has stopped waiting for leaves nothing behind: one whose turn comes too late is not made, and metadata that is written too late (the disk held it up while an import gave up and took its file away again) is removed again. Renames of one project are done one after the other, and the answer goes out the moment the rename stands, before the tidying up, so that a slow removal of the old entry cannot make the answer late and have the file put back under a rename that was kept. The answer gives the new and the old id and name; renaming a file to its own name changes nothing (it used to come back as `name_1`).
- A native export stops when a clip's media is not in the project, instead of leaving the clip out. The error names every such clip, picture and sound, with its track and time, and nothing is exported (HTTP 409). A hidden clip, a hidden track and a muted sound track do not stop it.
- `editor:media:info` and `editor:media:rename` answer `Media not found` (404) for an id the project does not have. `media info` used to answer success with no data, and `media rename` success with `false`.
- `editor:media:replace` leaves a file with the old item's name under that name. It was imported beside the old item as `name_1.ext` and stayed there after the old one was removed, so a script that finds media by file name lost it. It is now given the name back once the old item is gone, which also gives it the id the old item had. When that request fails, the command asks which name the file has before it reports one: the rename can have landed while its answer was lost.
- An adjustment layer under a media overlay exports natively. Such a timeline (a vignette track over a whole-film grade) was sent to the renderer engine, which takes no range, bitrate or `--keep-temp`. The layer is now graded inside the overlay pass, at its own track's place: it grades the tracks below it and leaves the overlays above it alone. A layer that is under an overlay and over text or a sticker (above every text and sticker track, or with one of them under it at the same time) still goes to the renderer: those are drawn after the overlays.
- The refusal of an override the renderer engine does not take says what can be done. It always ended "Drop them, or pass --engine muxer", and muxer is that same engine, so a range was refused again in the same words. It now says to drop them, names the one case where `--engine` alone was the trouble, and no longer writes "a adjustment layer".
- A paused preview shows the frame of `editor:timeline:seek`. With the pointer resting on the timeline the preview shows the hovered frame, and a seek (from the command line, the keyboard or a click elsewhere) moved the time and left that frame on screen until playback. A seek now ends the hover preview until the pointer moves again, also when the timeline scrolls or its zoom changes under the resting pointer.
- `editor:windows:focus` reports the window as it is once the focus has landed. It read the state straight after asking, and on macOS answered `focused: false` for a window it had just brought to the front.

### Changed

- A range export (`--start-time` / `--end-time`) is faster. The clips outside the range, which are encoded as black frames with their sound for the mix, are encoded several at a time, and the overlays, grades and text are drawn on the clips around the range only, not on the whole film. A 2-second range of a 300-second timeline of 150 clips with an overlay track, 100 sounds and the limiter on took 33 s and takes 17 s; the full export of it takes 98 s. The picture still matches the full export frame for frame (52 dB or better on every frame of four test timelines), and the sound is still the full mix cut to the range, which is most of what a short range now costs. With a transition, a drawn cursor or a keyframed grade in the timeline the whole picture is drawn as before.

### Added

- `editor:media:refresh` (see above).
