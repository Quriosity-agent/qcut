# 美体播放提速与循环验证（2026-10-20）

本轮沿用 `codex/body-playback-preview-1020`。目标是降低准备播放的重复成本，并补充音频输出、反复准备、取消及资源释放的证据。没有调整身体形变、检测、跟踪或模型计算规则。

所有真实素材、模型、原生库、缓存及画面对比均留在本机 `.local/body-playback-scaleup-20261020/`。源码清单和运行时绑定更新仅对应自研 Python 源码，私有资产清单未变。

## 已测到的提速

### 编辑器准备流水线

原先每帧依次完成合成、PNG 编码、OPFS 写入，再处理下一帧。现在仍串行调用原导出合成器，Canvas 同步取得位图快照后，允许其 PNG 编码与下一帧渲染重叠；按帧序提交缓存。

- 同一自研工程、180 帧、同一引擎清单、暖后端缓存：准备时间 **36.163 → 32.247 秒，缩短 10.8%**。
- 两次均没有启动新的模型推理；缓存及实际呈现画面逐帧等于既有导出。
- 同时最多两帧，像素预留预算 64MiB。1080×1920 实测峰值 24,883,200 字节；PNG blob 独立统计。
- 取消或任一阶段失败会停止提交，等待不能取消的 PNG 快照完成，然后释放代次资源。
- 指标是累加的分阶段耗时；重叠阶段的总和可能大于墙钟时间。

### 自研输入 PNG

只有首阶段为智能美体，且输入已是经过验证的规范 RGBA8 PNG 时，才将其复制到独立临时文件，省去一次等价的重新编码。保留原图解码、不透明校验、输入/输出哈希链及原生库隔离检查。含 EXIF、ICC、gamma、动画等其他元数据的输入仍走原来的规范化路径；最终输出压缩不变。

- 12 帧实际 provider 调用：12/12 输入命中快路径，12/12 RGBA SHA 与旧版一致。
- 除去模型加载首帧，同样 11 帧的平均调用耗时 **1080.578 → 932.358ms，缩短 13.72%**。
- 模型和形变阶段约 218ms，基本不变；不是模型推理优化。
- 冷启动首帧没有改善，不能按稳态结果声称冷启动更快。
- 旧性能基线未保存 PNG 文件哈希，因此实测对照只证明 RGBA；最终 PNG 字节相同另有 pipeline fixture 测试。

## 原生确定性源窗口缓存

仅处理 `freshTracking=true` 的独立 `source-window-v1` 请求；连续历史、按人脸定向和手工祛痘请求不直接复用。身份包含目标像素、全部预滚像素及顺序/时间、参数、引擎、模型、效果包、实现与环境。运行时内容变化会失效。

命中仍执行原 provider 的跟踪槽 LRU 和旧内存缓存副作用。同一个底层 source key 若随后转为连续请求，会先用保留的原输入完整恢复真实原生状态，然后继续；不使用估计的跟踪状态。保留的待恢复请求受现有四个 scope 上限约束。

磁盘条目是 gzip 无损像素，核对尺寸、长度和 SHA。缓存异常回到原来的原生渲染。取消会立即拒绝调用方；尚未启动的任务不会启动，已进入原生的完整命令序列继续结束，合法结果可留作以后复用。

### 并发与崩溃

写入、回收和预算核对使用跨进程 lease。内核独占的 loopback 端口随进程被强杀而释放，不依赖可能误判活进程的超时锁文件。端口由同一缓存目录的文件系统身份确定；端口冲突只能导致放弃缓存，不能抢占另一个写入者。等待 500ms 后当前缓存实例停用，保留原生路径。

2GiB 容量包括已提交条目及写入临时文件的峰值。下次取得 lease 后清除失去写入者的临时文件。真实子进程测试覆盖并发写入、SIGKILL、等待取消和预算；这不等于已验收原生渲染引擎本身的崩溃恢复。

跟踪槽切换和 LRU 对照是带有状态的 host mock 回归，验证调用顺序及结果契约；不能将其扩写为所有真实原生连续历史场景的像素验收。

### 真实原生 60 帧复核

`native-cache-r7b-60` 使用全新工程、独立空缓存、产品默认 Swing/CoreML，按冷准备→导出→暖准备→实际播放的顺序完成：

- 同一 1080×1920、30fps、60 帧工程，冷准备 **227.461 秒**，暖准备 **27.729 秒**，缩短 **87.81%**。
- 冷请求执行 494 次真实 host render（含预滚）；暖准备 60/60 命中，执行 0 次。
- 本轮导出的全部 60 帧 RGBA 等于上一版原生导出的对应帧；60/60 播放缓存帧再次等于本轮导出。
- 捕获到的实际呈现画面全部匹配；逐像素抓图运行覆盖 57 个播放帧，另一次轻量计时呈现 59 个播放帧、耗时 2.01384 秒。
- 解码上限维持 6 帧、49,766,400 字节；被终止缓存 owner 的目录被回收，活 owner 保留。
- 8 项 E2E 检查通过，无 page error 或控制台错误。这是重复准备提速，不代表第一次原生计算达到实时。

## 音频与循环验证口径

原素材无音频。测试保留原视频码流，加入本地生成的 48kHz PCM 标记，记录两份文件的 SHA 和 FFmpeg 参数。观察点在实际混音输出路径；原 destination 连接和增益不变，附加观察支路输出零。使用 `getOutputTimestamp()` 将检出的 PCM 标记映射到实际 Canvas 呈现事件。

音频 fixture 使用 `-t`/`-shortest` 截取视频；其结束处的解码边界与未截原片可能不同。它用于音画与循环验收，不与原片的旧版像素参考混用。

已完成的 `audio-cycles-r1` 为 3 轮×2 秒：每轮 4 个标记全部检出，最大音画偏差 16.67ms；每轮关闭后 OPFS、位图 live/bytes 全部归零；最后一次真实在途取消及重新准备通过。

`audio-cycles-r6-180x10` 已完成 **10 轮×6 秒**，120 个 PCM 标记全部检出，各轮 p95 和最大偏差均为 **50ms**，低于预设的 80ms/150ms 阈值。每个标记都有实际画面映射。每轮做准备、播放、三个位置跳播和关闭；真实 worker 在途取消只在末尾执行一次。

- 首次新工程准备 214.166 秒；其后九轮暖准备为 30.206–31.362 秒。
- 十轮关闭及最后取消/恢复后，OPFS 与位图 live/bytes 均归零；峰值仍为 6 帧、49,766,400 字节。
- 取消命中真实 worker frame 1，在部分缓存清空后完整重建 180 帧成功。
- 各轮清理后的 Electron 总工作集为 1111–1305MiB，没有持续单调增长；最后恢复后约 1138MiB。工作进程在空闲超时后退出，后续暖准备继续使用结果缓存。
- 无 page error。12 条 HTTP 401 控制台记录保留在原始证据中，未把它们当作渲染或音频通过证据。

RSS 是观测记录，没有据此声明不存在长期内存增长。音频结论限于固定单轨路由，不包含物理扬声器回录、导出音轨或音频总线重建。后续路由变更测试需要补充观察探针对 disconnect/reconnect 的追踪。

## 仍未完成的边界

- 首次推理仍慢于实时。当前优化主要减少重复计算及编解码成本。
- 播放缓存仍为整片无损 PNG、每代 2GiB。这批素材每帧约 3.6MB，约 20 秒就会到达上限；反复播放短片不等于分钟级连续时间线支持。
- 原生与自研算法差距没有因缓存优化而缩小。上一轮同参数 180 帧解码后 RGB 平均绝对差基线为 6.2053/255，本轮没有重测这组同参数全片差分；不能把各自预览/导出相同当作两引擎相同。
- 多人交叉、遮挡等更广素材，以及长时间播放和内存稳定性，仍需要扩大验收样本。
