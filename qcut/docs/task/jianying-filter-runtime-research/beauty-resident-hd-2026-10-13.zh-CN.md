# 自研美颜：常驻进程、竖屏与原尺寸处理

日期：2026-10-13。分支：`codex/beauty-resident-hd`，基于 `origin/master` 的 `8d1084380`。
本文路径以仓库的 `qcut/` 为基准。

## 改动

- Electron provider 默认使用一个串行 JSONL Python worker。每帧仍从当前输入重新检测和计算几何；复用导入模块和无状态 CPU ONNX 会话，不保留上一帧人脸跟踪结果。
- 会话按模型字节 SHA-256 和优化选项缓存，最多 16 项、256 MiB 模型序列化字节。此数值不是进程 RSS 上限。线程数和优化配置与逐次启动基线一致。
- Swift/Metal 阶段仍调用现有独立宿主，没有宣称 GPU 也已常驻。未改变排队、帧缓存或独立路径不回退原生的约定。
- 取消、超时、异常退出或错误响应会终止整个进程组，等待管道关闭后才允许下一个任务重新启动。正常空闲 60 秒回收；来源清单或环境变化会更换 worker。请求／响应和诊断都有大小限制。
- 保留 provider 的 `runJob: runIndependentBeautyJob` 注入，供相同源码的单次启动基线比较。生产默认走常驻路径。
- 从独立版回移原尺寸处理契约。预览模式的旧数学保持，最长边超过 1280 时显式使用 original 模式，处理源图尺寸保持不变；分析图仍有自己的 640 上限。
- QCut 统一限制最长边 4096、总像素 8,294,400；1080p 和 UHD 4K 横竖屏无需先缩到 1280。更大画布会按预算缩小处理，界面注明限制。
- 新增已绑定 SHA-256 的 `128×224` 和 `128×240` 皮肤分割 profile，覆盖 9:16 磨皮／美白及实测非方形像素素材的裁剪前画面。其它未列入清单的比例仍明确失败。
- 美颜实验室与时间线共用选择校验；启用的肤色资源、分人物或手动设置会明确拒绝。实验室导入使用高清预算，滤镜实验室维持自身的 640 默认值。

## 常驻性能实测

同一张 541×640 真人照片，相同源码的单次启动 provider 与常驻 provider 各执行三次，不使用帧结果缓存。计时包含每次完整性校验、PNG 编解码、推理与 Metal 子进程，排除初次 inspect 和证据文件保存。

| 调整 | 单次启动中位数 | 常驻热帧中位数 | 提速 |
| --- | ---: | ---: | ---: |
| 大眼 60 | 2.988 秒 | 0.445 秒 | 6.71 倍 |
| 磨皮 30＋美白 45 | 3.413 秒 | 0.718 秒 | 4.75 倍 |
| 磨皮＋美白＋瘦脸＋鼻形＋口红 | 10.575 秒 | 1.434 秒 | 7.38 倍 |

每一组的 RGBA、PNG 字节和尺寸均完全一致。常驻进程第一张五官照片仍需 2.924 秒初始化；后续皮肤和组合组复用同一个进程，表格的热帧值取各组后两次的中位数。此数据是本机短基准，不代表实时视频帧率或高清耗时。

逐次计时、PID、模型缓存命中数及输出哈希保存在 `benchmark/summary.json` 和逐帧 receipt。

测量主机为 Apple M4 Pro、48 GiB、macOS 26.6.2，环境记录见 `validation/host.json`。性能测量绑定此前源码清单 `3c4b3f77fcc97afceb09e80fc0be1139ef29b2322e3ffee392e73b8982ae01a5`；随后仅为新竖屏比例补充皮肤 profile 和相应测试，未更改渲染数学。原始基准文件保留，没有用后续运行改写计时。

## 竖屏、高清与恢复

基准直接调用真实两路 provider，原生每项重置跟踪。1080×1920 输入从 1650×1950 原片居中裁剪，没有拉伸或放大。结果如下：

| 输入及调整 | 自研耗时 | 与原生最大 RGB 差 | 不同像素 |
| --- | ---: | ---: | ---: |
| 1080×1920，磨皮 30 | 1.022 秒 | 0 | 0 |
| 1080×1920，美白 45 | 0.745 秒 | 0 | 0 |
| 1650×1950，磨皮＋美白＋瘦脸＋鼻形＋口红 | 3.919 秒 | 1 | 2,064 |

三项 alpha 均一致。完整原图、原生、自研和差分 PNG 保存在 `benchmark/`。本次实图覆盖到 1650×1950；UHD 的尺寸预算通过契约测试，但未在此记录中宣称完成 UHD 真人全效果验收。

后续真实时间线测试暴露了非方形像素边界：360×640、SAR 171:176 的视频在浏览器显示为 360×659，居中覆盖 1080×1920 画布时先处理 1080×1977。该比例需要 `128×240` 皮肤模型。补齐后，1080×1977 的单次进程与常驻进程 RGBA、PNG 字节完全一致；原生对照磨皮 40 最大 RGB 差 4，美白 45 为 1，二者组合为 5、平均 RGB 差 0.01272。此新增比例未达到 ≤1 的原生阈值，残差集中于磨皮，保留为明确缺口。未修改旧算法来拟合新样本。

此比例的静态原生对照使用 1650×1950 原片居中裁剪并轻微等比放大到 1080×1977，过程和 SHA 记录在 `cover-128x240/`。该补充验证不替代三项原尺寸高清测试。

两次早期 UI 测试发现导出错误被吞掉，结果是三张相同黑帧；失败视频和诊断保存在 `timeline-e2e/`、`timeline-e2e-r2/`，不能作为成功样本。修复在图片／视频效果回退、视频重试和外层媒体绘制边界传播自研错误；取消也立即传播。读取自研源图失败不会返回原图冒充成功。

真实 Electron 第三轮验收通过，耗时 48.9 秒，证据在 `timeline-e2e-r3/`：

- 9:16 画布启用磨皮 40、美白 45；暂停预览为 1080×1920，有 235,174 个像素相对原图改变。播放时不提交新的自研帧任务，常驻 worker 保持空闲。
- 导出 1080×1920、30 fps、三帧 MP4。三个源帧和三个导出帧的哈希分别不同，排除重复黑帧；首次无帧缓存导出 7.551 秒，缓存重导出 0.541 秒，两份视频解码后逐帧 RGBA MD5 完全相同，缓存条目没有增加。
- 在真实渲染子进程活跃时点击取消，旧进程组退出、缓存停止新增，未生成取消目标视频。
- 下一次导出期间向真实 Python worker 发送 SIGKILL，界面明确显示 `Independent worker exited`，未保存 MP4，旧进程组全部退出。
- 随后同样参数重新导出成功，使用新 worker，耗时 7.543 秒。三帧均不同；应用关闭后取消、崩溃、恢复的三个进程组全部消失。
- 正常阶段没有浏览器异常或美颜／导出错误日志。错误提示、恢复状态和暂停预览均有截图，并额外解码查看了导出第一帧。

该视频源本身为 360×640，高清导出测试验证的是处理尺寸、缩放裁剪、编码和恢复流程，不代表产生了原素材不存在的高清细节。0.1 秒的三帧样本也不构成长视频稳定性验收；本轮没有比较预览与导出之间的像素一致性。

恢复实测在组合渲染启动约 501 ms 后分别取消请求、向真实 worker 发送 SIGKILL：两次请求均拒绝，旧进程组退出，下次请求建立新 PID，RGBA 和 PNG 字节恢复到基线。取消后首次恢复耗时 4.380 秒，崩溃后 4.085 秒，包含重新初始化。高清处理后再次执行旧预览组合，输出仍完全一致，排除了分辨率模式残留。

除真实渲染恢复外，传输层测试覆盖超时、错误／超长响应、请求身份不符、父进程退出而子进程持有管道、空闲回收及来源身份变化。

审查另外修复了缓存查询阶段的取消竞态：帧任务在任何异步查询前登记，取消可中断身份读取、缓存命中／未命中和等待渲染；IPC 同时取消帧任务与底层队列。取消后不会新启动渲染、发起缓存写入或返回成功。取消前已开始写入的已验证缓存允许完成。销毁服务会先使帧任务失效；并发重复请求 ID 会拒绝。相关帧／队列／IPC 65 项测试通过。

新增帧包装与实际队列的组合测试，显式阻塞底层清理：旧帧取消会立即返回，第二个排队请求也可取消，最新请求等待清理完成后成功。只有首帧和最新帧进入 provider，只有最新帧写入缓存；帧与队列套件最终 21/21 通过。生产队列已保证此顺序，无需增加重复队列。

## 工程验证

- 完整 Python 回归：515/515 通过，71.4 秒。第一轮有一个 Metal 宿主 30 秒启动超时；单独 3 项复测通过后，全量第二轮通过。随后新增 `128×240` profile，其皮肤分割套件 12/12 通过。没有放宽超时或跳过测试，首轮日志保留。
- 常驻传输层 13 项真实子进程测试、provider 42 项测试通过；竖屏 profile、原尺寸契约、十类 Swift 宿主以及旧数学回归均纳入完整 Python 套件。
- 导出失败／恢复、过渡、图片缓存和导出预检共 24 项测试通过。覆盖图片与视频、自研 IPC 失败、取消、源图读取异常，以及静态参数为零但关键帧参数生效的情况；失败时不重试生成占位图或黑帧。
- 基准脚本 6 项测试、源码清单 staging、私有文件 provenance、全仓 12 个 TypeScript 项目检查及 Web／Electron 构建通过。最终 40 个改动 TypeScript 文件的 Biome 检查及 `git diff --check` 通过。
