# 美体分段预览、滚动缓存和调参重算（2026-10-20）

沿用 `codex/body-playback-preview-1020`。本轮解决整片 PNG 准备达到单代 2GiB 上限后无法继续的问题，并让已经开启的效果预览在调参后自动重建当前位置。长片验收还发现并修正了视频人脸输出错误套用照片画幅限制，以及有效 PNG 被误识别为 SVG 的问题。身体检测、形变、模型和后端历史恢复实现没有修改。

真实媒体、模型、原生库、PNG、MP4、运行日志及像素证据留在本机 `.local/body-playback-segmented-20261020/`。提交范围只有源码、测试和本文档。

## 准备与缓存

- 默认每段两秒。1080×1920、30fps 时每段 60 帧；根据未压缩 RGBA、PNG 开销和单代磁盘预算，较大画面会缩小每段帧数。
- 优先准备播放位置所在段，完成后即可显示，再准备下一段。缓存保留上一段、当前段和下一段；不会因时间线更长就预先生成整片。
- 远跳会取消不再需要的准备，等待已开始的渲染及 PNG 快照结束，再串行准备新目标。重复使用已缓存段时仍清理窗口之外的文件。
- 磁盘删除成功后才释放对应预算。删除期间取消、部分删除成功及目录中已不存在的帧，都按实际文件状态更新计数。
- 解码缓存最多六帧且不超过 64MiB。窄窗口进一步限制预读范围，防止尚未计划的远处读取占满并发槽，阻塞回跳。
- 2GiB 是单个活动预览代次的上限；既有清理规则仍允许保留一个删除失败的受管理孤儿目录，其他活动窗口也有各自缓存。因此不将这个数字描述为整个应用的磁盘总上限。

分段、范围准备和滚动调度分别放在 `canvas-playback-window.ts`、`canvas-composition-playback-preparation.ts`、`canvas-composition-playback-stream.ts`。原有缓存负责 OPFS 所有权和实际读写，reader 负责位图解码与释放。

## 调参、跳播和取消

开启效果预览后，参数或合成内容变化会立即停止旧代次并撤下旧画面；连续修改合并等待 150ms，然后从当前播放或拖拽位置准备新代次。显示缓存整代失效，只重建当前窗口；未改片段能否复用后端结果，仍由原来的完整缓存身份决定。

准备期间的拖拽目标一直保留到画布挂载，避免准备好新位置后又退回旧播放时间。换工程或明确关闭预览会清除自动准备意图；已经排队的旧定时器不能重新启动它。

自动重算适用于仍符合缓存预览条件的参数／合成修改。进入遮罩编辑、画布拖拽或展开预览等会使该模式暂时不可用的操作，也会清除准备意图；恢复条件后需重新点击准备。当前美体滑杆改参验收不覆盖这类模式切换后的自动恢复。

导出期间暂停后台预取，复用原导出路径。取消对已经进入原生的命令仍遵守既有完成规则；自研已运行的时序帧也允许完成并保存历史，调用方在返回后检查取消信号。旧代次的晚到结果不能重新显示。恢复时重新准备合法代次，不用旧参数的历史状态补画。

只有 URL、没有可验证文件内容的自研智能美体素材不进入这条准备路径，避免把可变化的 URL 当作源内容身份。非美体素材与原有导出行为不因此改变。

## 保留的跨帧合同

每一段仍使用完整工程计划和绝对时间线帧号：

`absolute frame → createCanvasCompositionRenderer → 原导出 renderFrame(frame / fps)`

没有把段首变成第零帧，没有加入“段边界 RESET”，也没有并行执行多个段的模型渲染。片段及媒体 ID 不因 UI 分段改变。

- 原生沿用已有 `source-window-v1`：`freshTracking` 配合真实源 PTS 预滚。既有预滚上限为 16 帧、0.5 秒和 64MiB。本轮没有把它改成另一种跟踪规则。
- 自研沿用片段内容及参数身份、检查点和有序历史重放。跳到未处理位置时仍补齐需要的历史；调参不会复用旧参数检查点。
- 滚动淘汰只删除已合成的预览 PNG，不删除或伪造算法检查点。

因此本轮验证目标是分段准备与既有导出合成器的像素一致性。这不能单独证明剪映编辑器任意长度连续历史与当前源窗口策略完全等价，也不能证明原生与自研算法已经相同。

## 长片发现的视频人脸边界

自研首次 24 秒导出在第 215 帧失败：人物走近镜头、额头越出上沿，一个已接受脸槽的关键点在 360×640 算法画幅中的最小 y 为 `-3.271036148071289`。视频公布阶段调用了只接受 `[0, 1]` 坐标的照片接口，抛出 `OutOfFrameLandmarks`。这次失败保留在本地 `independent-24-r1/failure-manifest.json`，不计为通过。

没有增加裁剪或丢脸容错。依据既有反编译中的 `DoOldStyle` 输出资格和新的独立原生探针，在原始 `DoTracking` 成功完成后，向一个已接受脸槽的四个点分别写入有限的左、右、上、下超界坐标，再经过原始 public FaceBuffer 输出。原生保留全部超界值，不修改槽的 active/new/ID/age、内部点或其他元数据；两张脸的 424 个浮点输出与自研转换逐位一致。该探针是明确标注的合成边界实验，不作为真实模型检测精度证据。

修复将同一 float32 坐标转换抽成 `normalized_coordinates`，视频公布使用它；照片 `normalized` 继续检查画幅范围。模型接受门限、脸槽选择、跟踪及恢复规则保持不变。

随后通过原编辑器解码链路保存第 204–215 帧的真实 RGBA，从失败前的检查点复现并验证修复：

- 第 215 帧三次捕获的输入 SHA-256 一致，为 `440de616be7e29fb68010b31c332f9004f70251574c008a85f727926f52fd417`。
- 修复前在第 215 帧同位置失败；修复后 12 帧全部完成。第 204–214 帧的 11 个输出 SHA-256 均保持不变。
- 第 215 帧保留原脸槽 ID 1、年龄 76 和超界点，输出 SHA-256 为 `3786eb3739117eeb1cd60f6ed204ebd58831b198f9fb086581d7568bb9494f6c`。
- 同一原生长片基线已正常通过对应的第 210–220 帧。后续自然预取第 215 帧时，只读捕获的输入 1080×1920 RGBA（8,294,400 字节）也与自研捕获的输入 SHA-256 完全相同，实际解码时间为 `7.1738333333333335` 秒，未额外发起渲染。原生使用原有 source-window 历史；同源输入证明本身不代表两种跟踪策略完全相同。

本地证据分别在 `native-publication-synthetic/`、`out-of-frame-input-probe/` 和 `out-of-frame-probe/`。探针二进制、模型、原始人脸张量及影像都未加入 Git。

## 长片发现的 PNG 读取问题

修正视频坐标后，新的自研完整编辑器运行通过了第 215 帧，但在第 332 帧遇到 `Invalid SVG image`。这次运行保留了第 0–331 帧的导出哈希和完整错误，仍计为失败。

精确重放表明，引擎输出是有效的 1080×1920 PNG，Pillow 回解的 RGBA 哈希与引擎报告完全相同。失败来自 `@napi-rs/canvas` 0.1.97 的 Buffer 入口：它在整个输入中搜索 `<svg`，该 PNG 压缩内容第 94,006 字节恰好包含这个序列，导致它先进入 SVG 解析。对应的文件路径入口会先识别 PNG。上游实现见 [固定版本的 image.rs](https://github.com/Brooooooklyn/canvas/blob/v0.1.97/src/image.rs)；实际私有图像、输入、输出报告和错误栈保存在 `png-decode-input-probe/`。

修复让 provider 直接解码独占任务目录中的 `owned.png`，并复核解码后的实际尺寸；缓存保留已验证的字节快照。普通缓存 PNG 仍在内存中解码，只有包含 `<svg` 的 PNG 才写入独占临时文件、通过同一 Skia 解码并在结束时清理，避免缓存原文件被滚动淘汰或替换的竞争。原有 PNG、RGBA、报告哈希和尺寸检查全部保留。

该问题属于图片读取链路，不是模型检测或形变算法错误。已有 335 个保留缓存 PNG 经旧 Buffer 入口、同一 Skia 的文件路径入口及原记录 RGBA 哈希三方核对，全部逐字节一致。真实第 332 帧经文件路径解码后也与引擎报告的 RGBA 哈希 `f041d1ebbde692145bc1bc43254babe9b944b6b9a7d64e59a99aa0f8fbef4611` 完全相同。

回归使用自造的合法 PNG 文本块复现格式碰撞，不上传私有图片。provider、缓存和视频相关的 121 项测试通过，覆盖缓存原文件删除／替换、无额外文件的普通 PNG、损坏数据、尺寸和像素哈希不符，以及临时文件成功／失败清理。在原生 E2E 并行期间，真实约 2.99MB 碰撞 PNG 的十次有效诊断样本中，临时文件创建、写入、删除合计中位数约 1.79ms；这不是独占设备基准。

r7 构建中另以原失败工程完成真实编辑器恢复：第 332 帧冷算返回 `rendered / cached=false`，回跳后返回 `cached=true`，两次 RGBA 均与上述引擎报告完全一致，页面没有错误。记录在 `png-decode-recovery-r7/`；该单帧恢复不替代下面的完整长片验收。

## 未改片段的缓存资格与临时锁恢复

原生首次 24 秒运行完成了 720 帧基线导出、720 个缓存 PNG、719 帧实际呈现和远跳／回跳的精确像素检查，但随后在“改 A 后 B 的所有请求应命中缓存”处失败。该次选中的 B660 对应原片约 11 秒，人物已经出画；原运行保留为失败，未执行的改参导出、取消和 72 秒步骤不算通过。

隔离缓存的真实 B660 探针证实，两次完整源窗口重放都返回合法原图 RGBA，与原导出逐字节一致，同时带有 `needsSourcePreRoll=true`，没有缓存相关 warning。这个标记是现有桥接层根据冷会话／之前仍需历史以及输出未改变作出的保守提示，并非原生二进制报告错误。既有缓存策略拒绝保存此类结果。本轮保留该规则，将未改片段复用检查移到 B 中人物仍在画面的区间；出画段继续参加全部 720 帧预览及 B 全部 360 帧导出的像素检查。

排查过程中另外发现了真实的临时锁恢复缺陷：一次 `CacheLeaseUnavailableError` 会永久停用该 provider 的缓存读写。隔离目录中的真实 B360 原生探针保留相同输入和八帧预滚，依次得到冷算 9 条命令、暖缓存 0 条；独占该缓存的内核锁约 4.3 秒后，捕获明确的锁超时，释放锁后两次仍各重算 9 条。五次 RGBA 全部与原 B360 导出一致。该受控故障证明独立的缓存恢复缺陷，不作为 B660 失败原因。

最小修复只删除永久停用开关，后续请求仍重新取得原锁、核对完整身份，再读写缓存；锁时限、2GiB 容量、取消和原生历史重放均未改变。三项恢复回归先失败后通过，相关缓存、身份、provider、磁盘与跨进程锁测试共 59 项通过。

r8 真实原生探针复用了相同目标 RGBA、八帧有序预滚、时间、尺寸和参数：冷算 9 条命令、暖缓存 0 条；持锁约 4.1 秒触发明确超时并正常原生重算；释放后连续两次重新命中缓存，均为 0 条原生命令。十个修复前后输出的 RGBA SHA-256 全部为 `807dabb97c3c9e7fc4d52eb5b0dc6553d6dd027b809c69a66eb04155a3fe828c`。隔离工程的 sourceKey 和请求 ID 各自独立，其他影响像素的输入和历史逐项相同；完整记录见本地 `native-lease-r8-r1/before-after.json`。该修复没有改变 B660 的历史重算资格。

## 真实验收设计

使用同一份私有 1080×1920 实拍素材，源帧率 24000/1001，时间线 30fps。24 秒工程由两个真实片段组成：A 使用源 0–12 秒、瘦身 40／长腿 30；B 使用源 1–13 秒、瘦身 55／长腿 20。它不是 24 秒单镜头跟踪样本。

原生和自研分别运行：

1. 完整导出 720 帧，记录编码前 RGBA SHA-256。
2. 分段播放，逐一核验累计 720 个真实 OPFS PNG，并核验捕获到的实际呈现画面；播放跨越每个段边界。
3. 远跳、回跳后逐像素核对；检查实际缓存文件、容量和淘汰。
4. 停在 B 时修改 A 的瘦身参数，验证新代次自动建立、B 复用既有后端结果。
5. 再导出 720 帧，验证 A 确实变化、B 全部保持原像素，并逐帧核对修改后的 A 预览。
6. 在真实渲染请求执行期间取消，验证无晚到显示、OPFS 和位图释放，再准备并核对恢复画面。
7. 将两个片段各复制两次，组成六片段 72 秒时间线，抽查 24、48、70 秒附近的缓存和跨边界播放。

72 秒检查明确是抽样，不是完整逐帧导出验收。参考映射只用于相同静态参数、裁剪时间和片段局部历史的复制片段；不扩展到关键帧、变速、转场或其他依赖绝对时间的效果。诊断播放会停下来检查即将淘汰的 PNG，耗时不作为无缓冲实时播放性能。

原生／自研另外配对保存的 10 张同参数基线 PNG，先核对各图解码后的 RGBA 哈希，再计算未经缩放或配准的差分。这些样本的 RGB 平均绝对差为 3.9996（通道范围 0–255），最大通道差为 194，任一 RGB 通道不同的像素占 30.6763%；其中包含人物已出画的零差异帧。这些数字只描述该样本集合，不能换算成“算法完成百分比”。腿部及周围背景仍存在可见形变差距。对照页同时提供原片、两套效果导出、实际绝对差分和仅供展示的八倍差分。

## 验收记录

原生首轮失败运行 `native-24-r1` 使用冻结的 r5 构建，启动源码提交为 `ce6dd92f79fd5879be3d1e292e6581843a10279d`；构建和当时源码指纹保存在本地 `build-source-lock-r5.json`。修正人脸边界后，自研使用 r6 独立引擎源码及对应的运行时清单。临时目录中完整编译的 1,124 个 Electron JS／JSON 产物，与 r5 相比只有独立运行时清单 JSON 不同；仅原子更新这一文件，原生运行中的代码、缓存身份目录和前端均未改变。详细文件哈希在 `incremental-build-r6-diff.json`。

修正 PNG 读取后生成 r7：同样核对 1,124 个编译产物，仅独立 provider 和独立帧缓存两个 JS 文件变化，并同步各自 sourcemap。Python 清单和运行时 pin 与 r6 相同，原生目录、入口 JS 和前端保持不变。新构建锁及逐文件核对分别为 `build-source-lock-r7.json`、`incremental-build-r7-diff.json`，启动源码提交为 `3c9b4bef95d004f0dd1221035873e38ac127ef97`。两端证据各自保留原始版本身份，跨引擎画面对比明确标注这一差异。

r8 再核对 1,124 个 Electron JS／JSON 产物，仅原生 `source-window-render-cache.js` 有变化，并同步其 sourcemap；前端、入口、自研 JS 和 Python 清单均与 r7 相同。原生完整复测使用 `c1ec661a6b068f5fce77006e24635e92d04c3566` 和 `build-source-lock-r8.json` 的 57 项文件指纹。测试使用独占原生磁盘缓存目录、默认 2GiB 预算；未改 B 段复用门禁要求目标区间 420–479 全部 60 个不同帧均命中且没有原生命令，重复回执不能代替缺失帧，相邻预取和自研历史重放不混入这项证明。请求／门禁及导出错误检测的 28 项回归通过。

原生与自研运行采用隔离工程及状态目录，没有改用其他推理设备配置来消除差异。两条引擎并行运行的耗时只作诊断，不作为独占设备性能基准。

原生冷算按原有源窗口逐帧重放，完整验收可能超过原定四小时。测试框架的总运行预算改为六小时；首轮 r5／`native-24-r1` 进行中的 worker 通过公开 `test.info().setTimeout` API 延长，并记录前后值及 worker 身份，随后关闭本机调试端口。当前 r8 复测启动时已使用六小时预算。像素、容量、覆盖率、测试步骤和生产运行时规则均未调整。这项时间预算变更不代表实时性能达标。
