### GRU：单帧通过，真实时序仍失败

已修复原生输出保留、FP16 展开和 CPU Softmax 配置。原始 arena 的 1,787,410 个参数与该模型固定哈希运行库的展开逐位一致，其中 50,253 个参数不能用标准 NumPy 展开代替。

6/6 单帧四输入/四输出用例通过，但 face/body 两段实际参考素材各 24 帧并完整重放，总计 96 次时序推理，完整四输出仅 2/96 通过。
三个循环状态的 288/288 次比较通过，两端各自的反馈和 reset/replay 也逐位正确；失败集中在最终概率 `nn_3`，最大差 `0.00390625`。

已将 native logits 单独送入移植 Softmax，输出逐位一致；524,288 个合成 Softmax 输出也逐位一致。
证据支持上游微小浮点差异跨过最终近似倒数的离散桶边界，但尚未消除该差异。
**因此整体仍判失败，不接入 `infer.py`，不放宽 `1e-4` 门槛。** 详细输入、首失败层与回放证据见 [GRU 记录](matting_route.zh-CN.md)。
CPU 候选专用加载器也默认拒绝，研究诊断必须显式传 `allow_unverified=True`。

## 关键数值问题

### 分类激活不等于通用 MobileNet 默认值

两份固定图编码的 hard-sigmoid 是 `clamp(x+4,0,8)/8`，hard-swish 是 `x * hard_sigmoid(x)`，SE 门控中的融合激活同样适用。套用常见的除数 6 会改变输出。通过终端前缀探针定位，再用未删层的完整图和保留输入验收。

### 原生 FP16 展开有版本特定行为

OCR 的原始 E 图和 half arena 不能直接交给低层 `Thrustor::CreateNet`。实际 loader 会去除 E 前缀、展开 half payload、保留末尾图标识。完整拓扑和输入占位不变。

这版 arm64 原生四元素 SIMD 转换对次正规数的 FP32 位表示额外 XOR `(half_magnitude << 13)`；尾部 1–3 元素走标准标量转换。直接使用 `np.float16.astype(np.float32)` 会改变 2,967 个 OCR 检测器参数。

已与原生导出函数比较全部 63,488 个有限 half 位模式、长度 1–8 的尾部用例和完整模型 arena，逐字节一致。这是固定哈希运行库的实证，不外推到所有 ByteNN 或 GPU。

## 共享工具

### 有边界的原生 CPU oracle

`bytenn_oracle.mm` 和 `bytenn_oracle.py` 提供固定图、FP32 输入输出的统一调用协议：

1. 校验指定运行库哈希；私有目录内创建新 case，保留 invocation、日志和输出。
2. 创建网络前强制 CPU；创建后必须回读 `GetForwardType()==0`。
3. 明确原生维度为 NWHC、内存为 NHWC，外部输入为 NCHW；检查全部声明形状。
4. `SetInput` 传字节数，随后回读输入逐字节核对，不能只看返回码。
5. 检查终端输出的路径边界、文件长度、有限值和全部输出名；失败保留报告。

该工具不自动解释 FP16、动态尺寸、量化整数或任意算子。OCR 动态尺寸、跟踪定点和 GRU 各有专用 oracle；不把不同 runtime 的成功状态混用。
共享 oracle 已在旧批次的人脸拟合和三输入降噪网络上实际复测通过。

### 统一推理入口

```sh
/opt/homebrew/bin/python3 research/local-model-pytorch/infer.py \
  --model .local/jianying-model-pytorch/ocr-det-20260919-verified/ocr-detector.pt \
  --input .local/jianying-model-pytorch/phase3-20260919/ocr-input.npz \
  --out .local/jianying-model-pytorch/phase3-20260919/ocr-output.npz
```

NPZ 必须按模型 blob 名命名。FP32 和 INT16 保留原始 dtype，不能静默把定点输入转成浮点；非跟踪模型只接受 FP32。多子网跟踪包需要显式 `--network`，其他模型不能忽略这个选项。
输出 JSON 记录模型及输入哈希、选定子网、输入输出 dtype/shape、CPU 耗时。模型仍需本目录的自写 Python 实现，并不是一个 `.pt` 文件脱离所有代码就能运行。

### 独立进程复测

`portable_smoke.py` 为每个 job 启动新 Python 进程，允许指定 `.pt`、NPZ 和输出目录，拦截 Python 审计事件中的原始私有资产读取、私有库加载和 socket 连接。
上一批 8 个包、新增 C73/舞蹈/OCR 检测 3 个包、跟踪 1 个包的四次子网运行，合计 **12 个包、15 个独立进程 job 全部通过**。检查输入和包哈希，保留每个子进程的退出码、日志与输出。
三个新增浮点包的独立进程输出与冻结 PyTorch 输出逐值一致，重比原生输出仍在固定门槛内；跟踪专用回放覆盖 52 个冻结 case，另有共享入口四个 job。

**这是 Python audit hook 范围内的运行时观察，不是 OS 沙箱、完整断网证明、跨平台验收或禁止所有 native syscall 的安全边界。** 不宣称已验证 Windows、Linux、CUDA、MPS 或剪映产品 GPU 路径。

### 不混淆资产与网络的台账

`conversion_ledger.py` 以 `source_sha256 + network_id` 为键，读取第二阶段索引和新增原生报告，重新计算每个 `.pt` 哈希。只有非空且全部通过的原生检查才接受通过状态。

- 一个源文件内的四个子网是四个网络，但仍然只有一个源文件。
- 同一网络 CPU 通过和旧 session 失败都保留在 history，不重复增加网络数。
- 多个网络共用一个 `.pt` 时按 artifact SHA 去重。
- 不从部分子网通过推导整个容器完整，不把失败候选放进 verified 列。
- 原报告中的 backend、scope、schema、图变换说明保留，不丢掉 CPU/动态尺寸等限定。

## 后续产品验收

1. 分类：恢复前处理、标签映射、阈值、脚本调用和时间聚合，再做真实素材语义验证。
2. OCR：完成识别器数值校准，再接检测图到框后处理、裁剪、CTC/字表、文本合并；检测器通过不是字幕识别通过。
3. 跟踪：单独验证模板/搜索特征、ROI、相关性/框解码及丢失策略；缓存 single-object 包不等于 QCut 当前 Bingo `.dat` 路径。
4. 抠像：CPU 模型对照之外仍需预处理、alpha 解码、连续帧独立状态反馈、reset/seek，以及编辑器预览/导出。
5. 分发：转换为 PyTorch 不改变源权重的权利状态，不能因此加入公开安装包。
